sip-b2bua.py -- signalling-only Back-to-Back User Agent
=======================================================

WHAT IT DOES
------------

An incoming INVITE creates a second dialog towards the destination in
the Request-URI:

    caller ---INVITE(A)---> [ B2BUA ] ---INVITE(B)---> callee

The second dialog is a new dialog, not a new call.  What changes between
the two legs is only what identifies the dialog or the hop:

    Call-ID          minted by the B2BUA before the INVITE is built
    From tag         newly generated by pjsip
    To tag           the callee's, not the one this B2BUA gave the caller
    CSeq             its own sequence space
    Contact          the B2BUA's own address
    Via / branch     rewritten per hop, as for any UA
    Max-Forwards     a fresh 70
    Route            from the outbound leg's own DNS lookup

User-Agent and Server are carried across by default, so the callee sees
the caller's User-Agent and the caller sees the callee's Server.  That
works without any SDK change: _cb_add_user_agent_hdr_impl() and
_cb_add_server_hdr_impl() in _core.ua.pxi only insert the engine's own
string when the header is absent, so a relayed one wins and no duplicate
is produced.  Only messages the B2BUA generates itself -- a 488, a 500,
a locally built 100 -- identify as the B2BUA, as "sipsimple-<version>".

--user-agent STRING applies to the OUTGOING LEG ONLY: requests sent to
the callee carry that User-Agent instead of the caller's.  Responses are
never touched by it -- whatever Server or User-Agent the callee put on a
response is relayed to the caller as it stands.  The engine's own
user_agent setting is deliberately left alone, because it would apply to
every message on both legs.

Everything else is carried across unchanged: the Request-URI, the From
and To URIs and display names, the SDP, and every other header that is
not dialog- or hop-specific -- P-Asserted-Identity, Diversion, Privacy,
Subject, Alert-Info, History-Info, Call-Info, X-* and so on.  The exact
exclusion list is NON_RELAYED_HEADERS in the script; anything not in it
is relayed verbatim in both directions, requests and responses alike.
So the two legs look like the same call to everyone except a dialog
matcher.

The SDP in particular is relayed unchanged, so the RTP flows directly
between caller and callee.  The B2BUA has no media transports, no
codecs, no sound device and no RTP ports.  It is a signalling box only,
in the spirit of sippy/b2bua's "no media" mode.

Routing is done by the outbound leg itself: an RFC 3263 lookup
(NAPTR -> SRV -> A) on the Request-URI of the incoming INVITE, through
sipsimple.lookup.DNSLookup.  No outbound proxy and no registration.
Authentication is handled -- see AUTHENTICATION below.

Concurrency: one B2BUACall object per call, all state changes serialised
on the twisted reactor thread; DNS runs in a green thread so slow
lookups never block other calls.  Parallel calls are the normal case.


RUNNING IT
----------

    ./sip-b2bua.py --udp-port 5080 --trace-sip

    --ip-address    bind address (default: all interfaces)
    --udp-port      UDP port, 0 disables (default: 5080)
    --tcp-port      TCP port (default: disabled)
    --tls-port      TLS port (default: disabled)
    --max-calls     concurrency limit (default: unlimited)
    --user-agent    identify as this string on both legs, overwriting the
                    peers' User-Agent and Server instead of relaying them
    --no-auth-relay do not relay challenges and credentials between legs
    --trace-sip     log every SIP message, both legs and unattributed
    --trace-inbound log only the caller leg's messages
    --trace-outbound log only the callee leg's messages
    --log-level     pjsip log level 0-5
    -v, --verbose   debug logging


WHY THE SDK NEEDED A PATCH
--------------------------

The SDK can do a B2BUA -- but only at the sipsimple.core.Invitation
level.  sipsimple.session.Session is the wrong layer: it insists on
building MediaStream objects, RTP transports and a local SDP of its own,
which is exactly what a media-less B2BUA must not do.  Invitation gives
raw access to the offer/answer:

  * Invitation.sdp.proposed_remote           the parsed remote offer
  * notification.data.body                   the raw offer/answer bytes
  * Invitation.send_invite(..., sdp=...)     send an offer
  * Invitation.send_response(code, sdp=...)  send an answer
  * Invitation.send_reinvite(sdp=...)        relay a re-INVITE
  * extra_headers=[...]                      relay arbitrary headers

What was NOT possible before the patch is byte-exact SDP relaying.  The
SDK has no opaque-body path: every SDP is parsed into pjmedia structures
and re-serialised, and worse, pjsip's SDP negotiator *re-derives* the
answer we hand it.  In pjmedia/sdp_neg.c, create_answer() clones our
"pre-answer", clears the media lines and rebuilds each of them with
match_offer(), which:

  * intersects the answer's formats with the offer's and drops the rest
    (together with their rtpmap and fmtp attributes),
  * reorders the remaining formats to follow the offer, because
    PJMEDIA_SDP_NEG_PREFER_REMOTE_CODEC_ORDER defaults to 1,
  * renumbers dynamic payload types to match the offer, because
    PJMEDIA_SDP_NEG_ANSWER_SYMMETRIC_PT defaults to 1,
  * rewrites the direction attribute from the offer's direction,
  * sets the port to 0 on any m= line it cannot match.

For a UA that owns the media that is all correct.  For a B2BUA that is
not in the media path it is a silent corruption: the caller would be
told to use payload type numbers that the callee will never send.

The patch adds a raw_sdp keyword to the three Invitation methods.  The
negotiator still runs (pjsip needs it to drive its own state machine),
but the body actually put on the wire is replaced with the exact bytes
we were given, after pjsip_inv_invite()/pjsip_inv_answer()/
pjsip_inv_reinvite() has built the message and before it is sent.

Files touched in python3-sipsimple:

  sipsimple/core/_core.util.pxi        new _set_raw_sdp_body() helper
  sipsimple/core/_core.pxd             its declaration
  sipsimple/core/_core.invitation.pxi  call_id= on send_invite(), to set the
                                       outgoing Call-ID instead of letting
                                       pjsip generate it. Safe after the
                                       dialog is registered because a UAC
                                       dialog set is keyed on the local (From)
                                       tag, not the Call-ID -- see
                                       dlg_set->ht_key in
                                       pjsip_ua_register_dlg();
                                       raw_sdp= on send_invite(),
                                       send_response(), send_reinvite();
                                       allow a 2xx without SDP when the
                                       offer/answer already completed in
                                       a reliable 18x (RFC 3262/3264)
  sipsimple/core/_core.sdp.pxi         BaseSDPSession.__str__ used a
                                       fixed 2048 byte buffer and
                                       returned '' for anything larger;
                                       it now grows the buffer
  sipsimple/core/_core.pyx             CORE_BUILD 16 -> 17

Rebuild with ./build_inplace (or python3 setup.py build_ext --inplace).
The script probes for raw_sdp at runtime and keeps working -- with a
warning -- against an unpatched SDK.


AUTHENTICATION
--------------

A 401/407 on the outbound leg is passed back to the caller together with
its WWW-Authenticate / Proxy-Authenticate header.  The caller answers
the challenge and re-sends the INVITE; the B2BUA copies its
Authorization / Proxy-Authorization header onto the new outbound INVITE.
This works because the digest response covers the method and the
digest-uri, and the B2BUA changes neither: the method is still INVITE
and the Request-URI is preserved end to end.  The nonce is relayed
verbatim and used exactly once, so nonce-count checking is happy too.

It breaks if the proxy binds the nonce to the source IP address or to
the Call-ID, because both change at the B2BUA.  OpenSIPS' auth_db does
neither by default.

The caller's retry arrives as a brand new INVITE -- the failed one was
answered with a non-2xx, so its dialog is gone -- which the B2BUA logs
as a new call.  That is normal.

Turn it off with --no-auth-relay.

This needed a second SDK patch: the stock _pjsip_msg_to_dict() in
_core.util.pxi *drops* Authorization, Proxy-Authorization,
Proxy-Authenticate and WWW-Authenticate outright.  pjsip parses those
four into dedicated structures rather than generic string headers, so
reading them as pjsip_generic_string_hdr would return garbage, and the
SDK chose to skip them instead.  They are now rendered with
pjsip_hdr_print_on() and exposed as ordinary FrozenHeader values, so
notification.data.headers carries them.

  sipsimple/core/_core.util.pxi   new _pjsip_hdr_to_frozen_header(),
                                  used for the four auth headers
  sipsimple/core/_core.pxd        its declaration and the
                                  pjsip_hdr_print_on() prototype

Caveat: those header values are credentials.  --trace-sip already prints
whole messages, but be careful about logging data.headers now that the
four are populated.

Unrelated bug found on the way: the Engine.user_agent setter in
_core.ua.pxi read

    self._user_agent = PJSTR(b"value")

so assigning to it set the literal string "value" rather than the value
assigned.  Fixed.


THE OPUS FIXUP MODULE
---------------------

This tree carries a local pjsip module ("mod-core-opus-fix", registered
in _core.ua.pxi at PJSIP_MOD_PRIORITY_TRANSPORT_LAYER+1) that rewrites
the opus rtpmap on every message:

  on receive  _cb_opus_fix_rx_impl rewrites "opus/48000/2" to
              "opus/48000/1" *in place* in the received buffer
  on send     _cb_opus_fix_tx_impl rewrites it back to "opus/48000/2"

Two consequences for the B2BUA.

1. It runs below the UA module, so the SDP the B2BUA reads out of
   notification.data.body has ALREADY been rewritten to
   "opus/48000/1".  What we relay therefore carries /1, and the TX side
   of the same module turns it back into /2 on the wire.  The relay is
   byte-exact with respect to what the rest of the stack sees, and the
   wire form is restored -- but do not be surprised by /1 in a Python
   level dump of the body.

2. _cb_opus_fix_tx_impl used to do

       new_body = pjsip_msg_body_clone(tdata.pool, body)
       sdp = <pjmedia_sdp_session *> new_body.data

   which is only valid for bodies built by pjsip's create_sdp_body(),
   where body->data really is a pjmedia_sdp_session.  A body made by
   pjsip_msg_body_create() -- which is what _set_raw_sdp_body() uses --
   stores raw bytes there, so the cast walked garbage and segfaulted
   (typically on a 200 OK retransmission, from tsx_retransmit ->
   endpt_on_tx_msg).  It now checks

       if body.print_body == pjsip_print_text_body:

   and applies the same fix textually and in place for raw bodies.  The
   replacement has the same length, so body.len and Content-Length stay
   correct.

   The general rule: anything in this tree that inspects an outgoing
   application/sdp body must not assume body->data is a
   pjmedia_sdp_session.


WHAT IS STILL MISSING / KNOWN LIMITS
------------------------------------

1.  SDP still has to survive pjmedia's parser and validator.  Limits
    from pjmedia/include/pjmedia/sdp.h: 16 m= lines, 32 formats per
    m= line, 68 attributes per m= line.  pjmedia_sdp_validate() also
    insists on a non-empty o= user, a non-empty s= line, IP4/IP6 address
    types, and an a=rtpmap for every dynamic payload type.  Offers that
    break any of those are rejected outright, so this is not a WebRTC
    relay.

2.  The negotiator can still refuse a perfectly valid answer if it does
    not "match" the offer by pjmedia's rules (no common format on any
    m= line -> PJMEDIA_SDPNEG_ENOMEDIA).  The script catches that,
    logs it, and fails the call with 488 rather than sending something
    wrong.  A real transparent relay would need a
    "pass-through" negotiator mode in pjsip (or
    pjsip_inv_answer() with the negotiator bypassed altogether) --
    that is the one thing the patch does not give you.

3.  Delayed-offer INVITEs (no SDP in the INVITE, offer in the ACK) are
    rejected with 488.  Relaying them would mean driving both legs'
    negotiators in the reverse direction.

4.  Multipart bodies are not handled: notification.data.body is the
    whole body, and only application/sdp is relayed.

5.  Only INVITE/re-INVITE/BYE/CANCEL are relayed.  In-dialog INFO,
    MESSAGE, UPDATE, REFER and PRACK-carried offers are not.  The core
    can receive them (Engine incoming_requests / Invitation.send_message,
    Referral), but nothing wires them across the two legs yet.

6.  No authentication on the outbound leg.  Invitation.send_invite()
    takes a Credentials object, so adding --username/--password is a
    handful of lines when a proxy starts challenging.

7.  No session timers, no NAT handling, no media inactivity detection,
    no CDRs.

8.  _pjsip_msg_to_dict() keeps only the first occurrence of a
    non-multi-valued header, so a 401/407 carrying two challenges for
    two different realms relays only one of them.

9.  FIXED, but worth knowing about: _str_to_pj_str() used to take the
    address of a temporary when handed a str -- it called .encode() and
    kept a pointer into the result, which was freed as soon as the
    expression ended.  pjsip then copied whatever happened to be at that
    address.  Invitation.send_response() passes the reason phrase
    through it, so relaying the callee's "200 OK" put

        SIP/2.0 200 <two bytes of freed heap>

    on the wire.  The caller's parser rejected the status line, never
    ACKed, and pjsip retransmitted the 200 forever -- which is also what
    the opus-fix segfault was triggered by.  It now keeps a bounded ring
    of the encoded bytes alive, and uses the byte length rather than the
    character count for slen.  _str_as_str()/_str_as_size() had the same
    shape (and encoded twice, so pointer and length could disagree) and
    now return the bytes object itself.
